# Slot Machine Arcade — full spec

## The pitch

Sam wants a slot machine for the arcade. You build it — reels, bets, a paytable — and then build the thing Sam actually needs: a record of every spin and statistics that prove what the machine pays back. By January it is a desktop game, a web API and a database — the same spins underneath all three. **Credits only; no real money anywhere.**

## Read this first: the thin-data risk

A slot machine has almost no data: a few symbols and a paytable. Without more, S5 (collections) and S7 (LINQ) have nothing to work on. **So in this theme the items are spins**, not symbols — every spin is recorded, and a session produces hundreds. The statistics screen is required, not a stretch.

## The domain

At least these, named however you like:

- **Spin** — the item. Id, time, bet, the three symbols, payout, credits after
- **Symbol** — an `enum`: Cherry, Lemon, Bell, Bar, Seven, Wild…
- **Reels** — a `record` of three symbols (a `record struct` works well). Paytable lookups compare it by value
- **Session** — the parent: player name, starting credits, started at
- **Your feature** — pick **one** and build it across the semester:
  - *Paytable & RTP* — the payout rules, and a simulation of 10,000 spins that measures return-to-player
  - *Bonus rounds* — three scatters give free spins; free spins are recorded and paid differently
  - *Player stats* — per session: biggest win, longest losing streak, credits over time

**Data:** at least **300 recorded spins** over at least **five sessions** — generated by playing, or by a seeded simulation.

## What each session adds

| S | Required feature | In this theme |
|---|---|---|
| 2 | 3+ types, an enum, an interface, zero nullable warnings | `Spin`, `Session`, `Reels` record, `Symbol`. A session's end time is nullable — a session still being played hasn't ended |
| 3 | 5+ tests over your own domain logic | The paytable: three sevens pay the jackpot, two cherries pay something, a wild completes a line; a bet above the balance is refused; the same seed gives the same spins |
| 4 | Abstract base + 2 kinds, a polymorphic loop, a switch expression | `PaidSpin` / `FreeSpin` (costs nothing, pays by different rules), each describing itself. **The switch is your paytable**: `reels switch { (Seven, Seven, Seven) => 100, (Cherry, Cherry, _) => 2, … , _ => 0 }` |
| 5 | Custom collection with indexer + iterator; a generic type | The history: `history[0]`, `history["sp-000142"]`, `foreach`. Your generic type holds the *last five results* shown under the reels |
| 6 | An event with 2 subscribers; a function as a parameter | "Spin recorded" — heard by the credit display and by the statistics. *Jackpot* is the stretch |
| 7 | 5 queries answering non-trivial questions | e.g. return-to-player per session · frequency of each winning line · longest losing streak · biggest win per player · average bet before a jackpot |
| 8 | Async save/load that survives a restart | The history to JSON, each kind back as its own kind. **Animation**: the reels spin with `await Task.Delay`, and the window never freezes |
| 9 | A window bound to the model | The machine (reels, bet, spin button) **and** the statistics view — the second one is what's graded most closely |
| 10 | 4 endpoints + DI + no secrets in source | `/items` — list, one, add, delete. A high-score board reads the spins |
| 11 | A migration + one one-to-many | **Session → Spins.** A spin belongs to one session; deleting a session keeps its spins |
| 12 | An attribute-driven feature + your own runner | `[Show("Payout")]` decides what the details panel lists. Your `[Check]`s test the paytable |

## At the end, you can show

1. The machine: bet, spin, reels animate, credits change
2. Your feature working — an RTP figure from 10,000 simulated spins, a bonus round, or a session's stats
3. Your five questions, answered on your data
4. The app closed and reopened, the history intact
5. The API answering in a browser, and refusing a POST without the key

## Stretch ideas

A jackpot event with a flashing banner · multiple paylines · sound · a leaderboard from the API.

## Watch out for

- **Random must be testable.** Pass in a `Random` with a seed. Unseeded randomness can't be tested and can't be demonstrated
- **The paytable decides everything.** Put it in one place, and let the simulation prove what it pays back
- **Credits, not money.** No purchases, no cash-out, nothing that looks like real gambling
